# Getlevant Supabase Architect Agent Guide

Purpose: Canonical guide for Getlevant backend conventions, RLS, migrations, and Edge Functions.

Tech Stack & Rules
- Database: Supabase PostgreSQL
- Server Logic: Supabase Edge Functions (Deno + TypeScript)
- Auth: Supabase Auth + Twilio Verify (Phone OTP)
- Currency: Fresh USD only (no LBP)
- Addressing: Free-text address, landmarks, lat/long (no postal codes)
- Communication: in-app push notifications primary; vendor's WhatsApp number is
  collected as a contact reference only (not wired to any automated messaging)

Critical Conventions

1) Order IDs
- Internal primary key `id`: UUID (use `gen_random_uuid()`)
- Human-friendly `order_number`: `SK-YYYY-XXXXX` generated by a DB sequence + trigger
- Store `order_number` as unique text for manual reference tracking

2) User Profiles
- Create `public.users` table that mirrors `auth.users` via a trigger on `auth.users` signup
- `users.role` enum: 'shopper', 'vendor', 'admin'
- Vendors must have a `store_id` (nullable for shoppers)

3) RLS Policies (required on EVERY table)
- Enable RLS on all tables: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`
- Use `auth.uid()` in policies to enforce identity
- Rules:
  - Shoppers: read/write only their own records (where `owner_id = auth.uid()` or `id = auth.uid()`)
  - Vendors: read/modify only data belonging to their `store_id` (compare row.store_id with user's store_id)
  - Admins: bypass filters (allow if `EXISTS (SELECT 1 FROM public.users WHERE id = auth.uid() AND role = 'admin')`)

Workflow for schema changes
- Draft migrations under `supabase/migrations/<timestamp>_<name>.sql`
- Use explicit RLS policies referencing `auth.uid()` (never rely on implicit JWT claims)
- After schema updates run:

```
npx supabase gen types typescript --local > src/types/supabase.ts
```

Example: Initial migration snippets

- Extensions & helpers

```sql
-- enable UUID generator
create extension if not exists pgcrypto;
```

- `public.users` and auth trigger

```sql
create table if not exists public.users (
  id uuid primary key,
  email text,
  phone text,
  role text not null default 'shopper',
  store_id uuid,
  created_at timestamptz default now()
);

-- function to mirror auth.users into public.users on signup
create or replace function public.handle_new_auth_user()
returns trigger language plpgsql security definer as $$
begin
  insert into public.users (id, email, phone, role, created_at)
  values (new.id, new.email, new.phone, 'shopper', now())
  on conflict (id) do nothing;
  return new;
end;
$$;

drop trigger if exists auth_user_created on auth.users;
create trigger auth_user_created
after insert on auth.users
for each row execute function public.handle_new_auth_user();
```

- Orders, sequence, and order_number trigger

```sql
-- sequence for human-readable order numbers
create sequence if not exists public.order_sequence start 1;

create table if not exists public.orders (
  id uuid primary key default gen_random_uuid(),
  order_number text unique,
  shopper_id uuid not null references public.users(id),
  store_id uuid not null,
  total_usd numeric(12,2) not null,
  status text not null default 'pending',
  metadata jsonb,
  created_at timestamptz default now()
);

create or replace function public.set_order_number()
returns trigger language plpgsql as $$
begin
  if new.order_number is null then
    new.order_number := 'SK-' || to_char(now(),'YYYY') || '-' || lpad(nextval('public.order_sequence')::text,5,'0');
  end if;
  return new;
end;
$$;

drop trigger if exists set_order_number on public.orders;
create trigger set_order_number
before insert on public.orders
for each row execute function public.set_order_number();
```

- RLS policy examples

A single `for all` policy on `public.users` using only `USING` (no `WITH CHECK`
that inspects the new row) lets a self-row match let a user write *any*
column on their own row — including `role` — so a shopper could promote
themselves to `admin`. Use per-operation policies instead, with a
security-definer helper to read the caller's role without RLS recursion:

```sql
alter table public.users enable row level security;

-- Reads the calling user's role without triggering RLS recursion on itself
create or replace function public.current_user_role()
returns text language sql security definer stable as $$
  select role from public.users where id = auth.uid()
$$;

-- SELECT: own row or admin
create policy "users_select" on public.users
  for select using (
    id = auth.uid()
    or public.current_user_role() = 'admin'
  );

-- UPDATE: own row via USING; WITH CHECK blocks self-promotion — the new
-- `role` value must match the currently stored value unless the caller is
-- already an admin.
create policy "users_self_update" on public.users
  for update
  using (
    id = auth.uid()
    or public.current_user_role() = 'admin'
  )
  with check (
    (id = auth.uid() and role = public.current_user_role())
    or public.current_user_role() = 'admin'
  );

-- INSERT: denied outright. Rows enter only via the security-definer
-- handle_new_auth_user() trigger on auth.users, which bypasses RLS.
create policy "users_insert_deny" on public.users
  for insert with check (false);
```

Orders follow the same "don't trust a client-supplied financial value"
principle. Revoke direct `insert`/broad `update` on `public.orders` and route
order placement through a `security definer` RPC (see `place_order()` in
`20260728000000_order_price_integrity.sql`) that re-derives every price from
`products.price_usd` server-side — never insert `subtotal_usd`/`total_usd`
directly from client input, and grant `update` only on the specific
non-financial columns a client legitimately needs (e.g. `status`, `notes`):

```sql
alter table public.orders enable row level security;

create policy "orders_shopper_owner" on public.orders
  for select using (
    shopper_id = auth.uid()
    or public.current_user_role() = 'admin'
  );

create policy "orders_vendor_store" on public.orders
  for select using (
    exists (select 1 from public.stores s where s.id = store_id and s.owner_id = auth.uid())
    or public.current_user_role() = 'admin'
  );

-- No insert policy for shoppers — orders are created via place_order() only.
revoke insert, update on table public.orders from authenticated, anon;
grant  update (status, notes) on table public.orders to authenticated;
```

Edge Functions guidance
- Use Deno + TypeScript. Keep business logic thin in DB when possible; validate inputs in Edge Function; use service_role key only server-side when necessary.
- Example workflow to create a function:

```
npx supabase functions new create-order
npx supabase functions deploy create-order
```

Security notes
- Never expose `service_role` key in client apps. Use Edge Functions for privileged operations.
- All tables must have RLS enabled and explicit policies.

Developer checklist (post-migration)
- Run local Supabase: `npx supabase start`
- Apply migrations: follow your migration tooling (`npx supabase db reset` if needed locally)
- Regenerate types: `npx supabase gen typescript --local > src/types/supabase.ts`
